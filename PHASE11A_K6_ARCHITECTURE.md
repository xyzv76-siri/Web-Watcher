# PHASE 11-A — K.6 Investigation Engine Architecture

Status: ARCHITECTURE FREEZE — REVISED
Phase: K.6 Investigation Engine
Date: 2026-08-17

## 1. Purpose

K.6 is the Investigation Engine layer.

K.6 executes an InvestigationPlan produced by K.5 and assembles a single
immutable InvestigationResult.

K.6 is the only layer in the investigation pipeline that:

- calls Tool.execute()
- tracks runtime budget consumption (steps_used, pages_checked)
- enforces timeout
- constructs InvestigationResult

K.6 does NOT construct InvestigationFinding (see §8).

K.6 is the terminal layer of the investigation pipeline. It does not
produce plans, does not suggest tasks, and does not expose internal
state.

## 2. Architectural Position

K.1 Investigation Contract
        ↓
K.2 Investigation Evidence
        ↓
K.3 Investigation Result
        ↓
K.4 Investigation Tool Layer
        ↓
K.5 Investigation Planner
        ↓
K.6 Investigation Engine   ← THIS LAYER

The architectural data flow is:

    K.5 Planner
        ↓  produces
    InvestigationPlan
        ↓  consumes (K.6 receives this directly)
    InvestigationEngine
        ↓  executes
    PlanStep
        ↓
    step.tool.execute(step.task, context)
        ↓
    ToolResult

K.6 receives an InvestigationPlan. It does not receive a Planner,
does not call Planner.plan(), and does not own the Planner.

## 3. Dependency Boundary

K.6 depends on:

- K.1: InvestigationPolicy
- K.2: Evidence, EvidenceType
- K.3: InvestigationStatus, InvestigationFinding, InvestigationResult
- K.4: Tool, ToolResult
- K.5: PlanStep, InvestigationPlan, PlannerError
- stdlib: time.monotonic(), dataclasses, typing

K.6 must NOT depend on:

- K.5 Planner class (K.6 receives InvestigationPlan, not Planner)
- K.5 ToolProvider (K.5's concern)
- K.5 InvestigationTask via Planner (K.6 receives task from PlanStep)
- Phase 10 AI modules (ai_contract, decide, final_decision, etc.)
- Network access (requests, httpx, urllib, socket)
- subprocess
- External storage

K.6 must not modify K.1, K.2, K.3, K.4, or K.5.

## 4. Responsibilities

K.6 is responsible for:

- receiving an InvestigationPlan (pre-generated by K.5)
- extracting the single PlanStep from the plan
- executing the PlanStep by calling step.tool.execute(step.task, context)
- tracking steps_used (PlanSteps whose Tool.execute() was actually entered)
- tracking pages_checked (sum of ToolResult.pages_fetched, no clamping)
- enforcing InvestigationPolicy.max_steps at runtime (pre-execution budget check)
- enforcing InvestigationPolicy.max_pages at runtime (post-execution budget check)
- enforcing InvestigationPolicy.timeout_seconds at runtime
- collecting Evidence from ToolResult.evidence into the global evidence tuple
- assigning zero-based positional indices to collected evidence
- determining the final InvestigationStatus per §10
- constructing a complete, valid InvestigationResult with findings=()
- providing a human-readable summary
- providing a failure_reason for FAILED/TIMEOUT/BUDGET_EXCEEDED statuses

K.6 is NOT responsible for:

- generating plans (K.5)
- suggesting tasks (K.5 / ToolProvider)
- calling Planner.plan()
- performing Task → Tool matching (K.5)
- re-planning after execution
- retrying Tool.execute() on failure
- constructing InvestigationFinding (see §8)
- inferring semantic meaning from Evidence
- determining whether a claim is supported or contradicted
- inferring INCONCLUSIVE from absence of evidence
- dynamic replanning
- caching results
- notifying external systems
- integrating with Phase 10 decisions

## 5. Execution Model

K.6 executes exactly one plan step in the current Phase 11-A architecture.

The Execution Model:

    InvestigationPlan (input)
        → plan.steps[0]  (single PlanStep)
            → PlanStep.task
            → PlanStep.tool
                → tool.execute(task, context)
                    → ToolResult

The Engine does not:
    * loop over multiple PlanSteps (single-step plan only)
    * call Planner.plan()
    * retry Tool.execute() on failure
    * construct alternative plans
    * select or replace the Tool
    * perform Task → Tool matching

Retry, multi-step execution, and replanning are explicitly out of scope
for Phase 11-A K.6.

## 6. Engine Input Boundary

The Engine's public input is an InvestigationPlan.

The Engine does NOT accept a Planner as a constructor dependency.

The Engine does NOT own or instantiate a Planner.

This boundary is mandatory and enforced by the architecture:

    WRONG:
        engine = Engine(planner=planner)
        result = engine.investigate()

    CORRECT:
        plan = planner.plan(task=..., context=...)   # K.5
        engine = Engine(policy=policy)
        result = engine.execute(plan)                 # K.6

The Engine must not:
    * store a Planner reference
    * call Planner.plan()
    * access Planner policy via property access
    * pass context to Planner

The InvestigationPlan contains everything the Engine needs:
    * PlanStep.task  → which InvestigationTask to execute
    * PlanStep.tool  → which Tool to call

## 7. Context Forwarding

K.6 does not construct the context. The context is passed through
from the caller via Engine.execute(plan, context=...).

The context is a Mapping[str, str] that K.6 forwards unchanged to
Tool.execute().

The context must:
    * contain only str keys and str values
    * not contain secrets, API keys, or raw response bodies

K.6 does not add, remove, or derive context keys.

If the caller provides context=None, K.6 passes an empty dict
to Tool.execute().

## 8. Finding Construction Boundary

Evidence is not equivalent to a semantic Finding.

An Evidence instance contains:
    * source, url, retrieved_at
    * claim, supporting_text
    * evidence_type

A Finding contains:
    * claim (a user-defined claim being evaluated)
    * finding_status (supported/contradicted/unverified)
    * evidence_refs (positional references to Evidence)

Evidence.claim is raw text from a source. It is not a finding claim.
A finding claim represents a question or assertion under investigation.
These are semantically distinct concepts.

K.6 does NOT construct InvestigationFinding instances.

K.6 does NOT infer:
    * claim (a finding claim is a user-supplied question, not a source claim)
    * finding_status (supported/contradicted/unverified requires semantic judgment)
    * truth value of any claim
    * relationship between multiple pieces of evidence
    * AI/LLM interpretation

K.6 uses:

    findings = ()

This is the correct and complete representation for Phase 11-A K.6,
given that no existing K.1–K.5 contract provides a legitimate
Finding producer.

If a future architecture layer (e.g., an AI evaluation layer) produces
InvestigationFinding instances, K.6 may consume them as input. In the
current Phase 11-A architecture, no such producer exists.

## 9. Evidence Collection and Indexing

K.6 collects Evidence instances from ToolResult.evidence.

For each ToolResult:

    for ev in tool_result.evidence:
        collected_evidence.append(ev)

The final InvestigationResult.evidence tuple is the ordered concatenation
of all collected evidence from all ToolResult instances.

### 9.1 Positional Index Assignment

Evidence indices are zero-based and assigned in collection order:

    evidence[0] ← first Evidence from first ToolResult
    evidence[1] ← second Evidence from first ToolResult (if present)
    ...
    evidence[n] ← last Evidence from last ToolResult

### 9.2 Empty Evidence Handling

If a ToolResult has an empty evidence tuple (success=False or no evidence),
no Evidence instances are collected.

The evidence tuple may be empty. This does not cause an error.

### 9.3 evidence_refs

InvestigationFinding.evidence_refs references the final global evidence
tuple using zero-based positional string indices.

Example:

    evidence = (
        Evidence A,  # index "0"
        Evidence B,  # index "1"
    )

    finding.evidence_refs = ("0", "1")

K.6 must preserve evidence ordering and must not invent evidence IDs.

K.6 does not assign evidence_refs because it does not construct findings.

## 10. Status Determination

K.6 determines the InvestigationStatus based on execution outcomes.

### 10.1 Possible Statuses

The Engine may produce exactly these statuses:

    SUCCESS
    FAILED
    TIMEOUT
    BUDGET_EXCEEDED

The Engine does NOT produce INCONCLUSIVE. See §11.

### 10.2 Status Rules

The status is determined after all execution completes, applying these
rules in deterministic order:

    Rule 1: TIMEOUT
        If the pre-execution deadline check or post-execution deadline
        check determined that the engine's elapsed time exceeded
        policy.timeout_seconds, status = TIMEOUT.

    Rule 2: BUDGET_EXCEEDED
        If pages_checked exceeds policy.max_pages after accumulating
        ToolResult.pages_fetched, status = BUDGET_EXCEEDED.

    Rule 3: FAILED
        If a PlannerError occurred (plan was invalid before execution),
        OR Tool.execute() raised an unexpected exception,
        OR ToolResult.success is False,
        status = FAILED.

    Rule 4: SUCCESS
        If no timeout, no budget exceedance, no failure condition,
        status = SUCCESS.

### 10.3 Multiple Conditions

If multiple conditions are observed (e.g., timeout and budget exceedance
both true), the rule with the lowest rule number wins:

    TIMEOUT          (Rule 1)
    BUDGET_EXCEEDED  (Rule 2)
    FAILED           (Rule 3)
    SUCCESS          (Rule 4)

### 10.4 Timeout Classification Detail

TIMEOUT is classified only when the Engine's own deadline semantics
establish it:

- Pre-execution deadline guard: elapsed time exceeds timeout_seconds
  before Tool.execute() is called
- Post-execution deadline guard: elapsed time exceeds timeout_seconds
  after Tool.execute() completes

TIMEOUT is NOT classified based on:
- arbitrary exception classes raised by Tool.execute()
- tool-specific timeout attributes
- timeout keywords in error messages
- any signal not originating from the Engine's own deadline monitoring

The Engine distinguishes:

- Timeout classification / deadline enforcement: guaranteed by §17
- Hard interruption / cancellation: NOT guaranteed under the current
  synchronous Tool contract

If Tool.execute() blocks beyond the deadline and no cancellation
mechanism exists, the Engine classifies the completed execution as
TIMEOUT after the tool returns. The Engine does not attempt to cancel
a blocking synchronous call.

## 11. INCONCLUSIVE Boundary

K.6 does NOT produce InvestigationStatus.INCONCLUSIVE.

INCONCLUSIVE requires a semantic judgment that the investigation was
performed but did not yield conclusive evidence. This judgment requires
either:

- a contract-specified signal from K.1–K.5 (none exists)
- an AI/LLM interpretation (out of scope for K.6)

No existing K.1–K.5 contract provides such a signal.

Therefore K.6 uses only the four statuses documented in §10.1:
SUCCESS, FAILED, TIMEOUT, BUDGET_EXCEEDED.

If a future architecture layer introduces a legitimate INCONCLUSIVE
producer, that layer will handle INCONCLUSIVE generation. K.6 will not
generate INCONCLUSIVE based on absence of evidence, low confidence,
sparse data, or any heuristic.

## 12. Failure Handling

### 12.1 PlannerError

If the InvestigationPlan is invalid (e.g., PlannerError was raised during
plan construction), K.6 returns:

    InvestigationResult(
        status=InvestigationStatus.FAILED,
        summary="planning failed",
        findings=(),
        evidence=(),
        confidence=0.0,
        steps_used=0,
        pages_checked=0,
        failure_reason=<PlannerError message>,
    )

PlannerError does not cause the Engine to raise. It is captured in the
result.

### 12.2 Tool Execution Exception

If tool.execute() raises an unexpected exception:

    InvestigationResult(
        status=InvestigationStatus.FAILED,
        summary="tool execution failed",
        findings=(),
        evidence=(),
        confidence=0.0,
        steps_used=<completed steps>,
        pages_checked=<accumulated pages>,
        failure_reason=<exception message>,
    )

The exception does not leak through the Engine's public execution
boundary. It is captured in the result.

### 12.3 ToolResult success=False

If ToolResult.success is False, K.6 does NOT continue normally.

The status is FAILED.

    InvestigationResult(
        status=InvestigationStatus.FAILED,
        summary=<from ToolResult.message or generic>,
        findings=(),
        evidence=<collected evidence before failure>,
        confidence=0.0,
        steps_used=1,
        pages_checked=<accumulated pages>,
        failure_reason=<from ToolResult.message>,
    )

pages_fetched from the failed ToolResult is still accumulated.

### 12.4 Timeout During Execution

If the Engine's deadline check triggers:

    InvestigationResult(
        status=InvestigationStatus.TIMEOUT,
        summary="investigation timed out",
        findings=(),
        evidence=<evidence collected before timeout>,
        confidence=0.0,
        steps_used=<completed steps>,
        pages_checked=<accumulated pages>,
        failure_reason="investigation exceeded timeout_seconds",
    )

TIMEOUT is classified only through the Engine's own deadline mechanism
(§17). It is not inferred from tool-specific exceptions.

## 13. Engine Error

K.6 defines a single engine-specific exception:

    EngineError

EngineError covers engine-level failures including:

- invalid InvestigationPolicy (e.g., negative max_steps before K.1 guard)
- null or invalid InvestigationPlan
- internal execution failure (unexpected exception in engine logic itself,
  not from Tool.execute())

EngineError is not raised for tool-level failures. Tool-level failures
are captured in the InvestigationResult.

## 14. Budget Enforcement

### 14.1 max_steps

steps_used = number of PlanSteps for which Tool.execute() was actually entered.

Pre-execution budget check:

    if steps_used + 1 > policy.max_steps:
        status = BUDGET_EXCEEDED
        # Tool.execute() is NOT called
        # steps_used remains unchanged

If Tool.execute() is entered:
    steps_used = steps_used + 1
    # Regardless of whether Tool.execute() succeeds or raises

If Tool.execute() raises:
    steps_used = 1 (the step was entered)
    status = FAILED (not BUDGET_EXCEEDED)

### 14.2 max_pages

pages_checked accumulates actual ToolResult.pages_fetched values.

    pages_checked = pages_checked + tool_result.pages_fetched

No clamping, no rewriting of actual values.

Example:

    max_pages = 10
    pages_checked = 8
    ToolResult.pages_fetched = 5

    → pages_checked = 13
    → status = BUDGET_EXCEEDED

The actual ToolResult.pages_fetched value (5) is preserved as-is in the
accumulation.

Post-execution budget check:

    if pages_checked > policy.max_pages:
        status = BUDGET_EXCEEDED

This check occurs after pages_fetched is accumulated, before the final
result is constructed.

### 14.3 Timeout

See §10.4 and §17.

The timeout check does not prevent Tool.execute() from being entered.
The pre-execution guard checks whether the deadline has already been
exceeded before entering a step.

    if time.monotonic() - start > policy.timeout_seconds:
        status = TIMEOUT
        # Tool.execute() is NOT called

## 15. State Model

K.6 is stateless across invocations.

The Engine must not retain:
    * previous InvestigationResults
    * previous Plans
    * previous ToolResults
    * evidence between runs
    * page counters between runs
    * step counters between runs

All runtime state is scoped to a single investigation execution and
discarded upon completion.

## 16. Determinism

K.6 must be deterministic for identical inputs.

For a given InvestigationPlan, Tool implementation behavior, and context,
K.6 produces identical InvestigationResult instances (modulo wall-clock
timing, which affects only TIMEOUT determination).

K.6 does not use:
    * random selection
    * current timestamp as a logic input (time.monotonic() is used
      only for timeout enforcement)
    * object identity
    * insertion order of unordered collections

## 17. Public API Scope

The minimum public conceptual API is:

    Engine
    EngineError

The Engine executes an InvestigationPlan and returns an
InvestigationResult.

The following are NOT part of the K.6 public API:

- Planner (K.6 does not own or reference a Planner)
- ExecutionContext
- EngineState
- EngineConfig
- ResultBuilder
- FindingBuilder
- EvidenceCollector

Internal helpers may be introduced during implementation only when they
do not expand the public architecture or violate frozen boundaries.

## 18. Minimum Engine Contract

The minimum public Engine contract is:

    class Engine:
        def __init__(
            self,
            policy: InvestigationPolicy,
        ) -> None:
            ...

        def execute(
            self,
            plan: InvestigationPlan,
            context: Mapping[str, str] | None = None,
        ) -> InvestigationResult:
            ...

The Engine receives:
    * policy: InvestigationPolicy (for budget and timeout enforcement)
    * plan: InvestigationPlan (produced by K.5 Planner)
    * context: optional Mapping[str, str] forwarded to Tool.execute()

The Engine does NOT:
    * receive a Planner
    * call Planner.plan()
    * store a Planner reference

The caller (outside K.6) is responsible for:
    * configuring the Planner with tools, policy, and optional ToolProvider
    * calling Planner.plan() to produce an InvestigationPlan
    * passing the plan to Engine.execute()

Example call flow:

    planner = Planner(tools, policy, tool_provider)
    plan = planner.plan(task=task, context=context)
    engine = Engine(policy=policy)
    result = engine.execute(plan, context=context)

## 19. Timeout Implementation Detail

K.6 uses time.monotonic() for elapsed-time measurement.

The timeout check consists of two guards:

    1. PRE-EXECUTION DEADLINE GUARD:
        start = time.monotonic()
        # ... engine setup ...
        if time.monotonic() - start > policy.timeout_seconds:
            # Deadline already exceeded before entering the step
            # Tool.execute() is NOT called
            # status = TIMEOUT

    2. POST-EXECUTION DEADLINE GUARD:
        elapsed = time.monotonic() - start
        if elapsed > policy.timeout_seconds:
            # Tool.execute() returned but deadline was exceeded
            # status = TIMEOUT

Classification vs. Cancellation:

K.6 provides timeout classification and deadline enforcement. It does
NOT provide hard interruption or cancellation.

If Tool.execute() blocks for longer than timeout_seconds and no
cancellation mechanism exists in the Tool contract, the Engine waits
for the call to return and then classifies the result as TIMEOUT.

The Engine does NOT:
    * use time.sleep() to wait for timeout
    * perform busy-wait polling
    * use threading for timeout enforcement
    * use signals or threads to interrupt Tool.execute()

## 20. InvestigationResult Construction Rules

The Engine constructs InvestigationResult with these rules:

    status: determined by §10 rules
    summary: human-readable string describing the execution outcome
    findings: ()
    evidence: tuple of Evidence (collected from ToolResult.evidence,
              zero-based positional order preserved)
    confidence: 1.0 if SUCCESS, 0.0 if FAILED/TIMEOUT/BUDGET_EXCEEDED
    steps_used: number of PlanSteps for which Tool.execute() was entered
    pages_checked: sum of actual ToolResult.pages_fetched (no clamping)
    failure_reason: "" for SUCCESS, descriptive string otherwise

The confidence rule:

    SUCCESS:          1.0
    FAILED:           0.0
    TIMEOUT:          0.0
    BUDGET_EXCEEDED:  0.0

INCONCLUSIVE is not produced by K.6 and therefore has no confidence
mapping.
