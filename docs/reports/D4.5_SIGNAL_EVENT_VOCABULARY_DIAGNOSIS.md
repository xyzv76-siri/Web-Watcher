## 1. Production Signal Vocabulary — 唯一值 `content_change`

**生产代码中 `signal_type` 的赋值点只有 1 个：**

```
fetch_service.py:134  signal_type="content_change"
```

**触发条件（唯一条件）：**
```python
# fetch_service.py:119-135
if old_hash is None:
    changed = True      # 首次拉取
elif old_hash != content_hash:
    changed = True      # content_hash 变化
else:
    changed = False

if changed:
    signal = Signal(
        id=None, entity_id=entity_id,
        signal_type="content_change",  # ← 唯一的 signal_type
        observed_at=fetched_at, value=content,
        fingerprint=content_hash,
    )
```

**结论：整个 production codebase 只有一种 signal_type：`"content_change"`。没有 `"stars_increased"`、`"new_commit"`、`"description_changed"`、`"open_issue_spike"` 等。**

- `event.status` — **0 个赋值点**（除测试 mock 外）

### 2.2 Event Correlator（`event_correlator.py`）

```python
@staticmethod
def _derive_event_type(signal: Signal) -> str:
    """
    从 Signal 推导出 event_type。

    当前实现是占位符——返回 signal.signal_type
    生产版本会映射到业务事件类型（如 'stars_changed' → 'trending'）
    """
    return signal.signal_type   # ← 直接透传 signal_type

@staticmethod
def _classify_importance(signal: Signal) -> str:
    return "important"          # ← 硬编码，忽略所有 signal 数据

@staticmethod
def _derive_status(signal: Signal) -> str:
    return "active"             # ← 硬编码，忽略所有 signal 数据
```

**三个 classification 方法全部是 stub：**
- `_derive_event_type`：直接 `return signal.signal_type` — 即 `"content_change"` 透传。
- `_classify_importance`：永远返回 `"important"` — 无分级逻辑。
- `_derive_status`：永远返回 `"active"` — 无生命周期逻辑。

**所有信号被分类为：`event_type="content_change"`, `importance="important"`, `status="active"`。**

### 2.3 关于 `_derive_event_type` 的旧诊断更正

D4 诊断声称："`_derive_event_type` 存在且把 `content_change` 映射为 `DISCARD`"。

**经 D4.5 验证，该说法不正确：**
- `_derive_event_type` 确实存在（`event_correlator.py:95-102`），但它直接 `return signal.signal_type`（透传 `"content_change"`），并未做任何映射。
- `"DISCARD"` 仅出现在 `final_decision.py:82`（`DecisionOutcome` 枚举）和 `decision.py:260`（`not_decision()` 返回 `"discard"`），属于**决策语义**，与 event classification 无关。
- `_derive_event_type` 中的注释声称"生产版本会映射到业务事件类型"，但**从未实现**。

## 3. GitHub API 原始指标层 — 未用于信号分类

### 3.1 Adapter 从 GitHub API 获取的完整数据（`snapshots.py` + `github_repository_adapter.py`）

| 字段 | 类型 | 来源 | 当前用途 |
|------|------|------|----------|
| `name` | str | `payload["name"]` | 仅存快照 |
| `full_name` | str | `payload["full_name"]` | 仅存快照 |
| `description` | str\|None | `payload.get("description")` | 仅存快照 |
| `stars` | int | `payload["stargazers_count"]` | 仅存快照 |
| `forks` | int | `payload["forks_count"]` | 仅存快照 |
| `open_issues` | int | `payload["open_issues_count"]` | 仅存快照 |
| `pushed_at` | str\|None | `payload.get("pushed_at")` | 仅存快照 |
| `updated_at` | str\|None | `payload.get("updated_at")` | 仅存快照 |
| `content_hash` | str | FetchService 计算 | 唯一 change detection |

**9 个字段全部被采集，但只有 `content_hash` 参与 change detection。其余 8 个字段零消费。**

### 3.2 缺失的细粒度 change detection

FetchService 的 change detection 仅基于 `content_hash`（整个 payload 的 JSON canonical hash）。这意味着：

- Stars 从 100→200：`content_hash` 变化 → 发 `"content_change"` 信号（但丢失了"stars 变了"这个信息）
- Description 被修改：`content_hash` 变化 → 发 `"content_change"` 信号（但丢失了"description 变了"这个信息）
- Pushed_at 更新（新 commit）：`content_hash` 变化 → 发 `"content_change"` 信号（但丢失了"有新代码"这个信息）

**所有变化都被压缩为一个无差别的 `"content_change"` 信号。**

### 4.2 Production context 的实际内容

context = {
    "policy_id": decision.policy_id or "",
    "target_key": decision.target_key,

### 4.3 接口不匹配矩阵

| InvestigationPlan scope | 是否有匹配的 production 值 | 结论 |
|-------------------------|---------------------------|------|
| `scope={"signal_type": "content_change"}` | ✅ 总是匹配 | 只有这一种能匹配 |
| `scope={"stars": "any"}` | ❌ context 中无 `"stars"` | 永不过滤 |
| `scope={"event_type": "new_commit"}` | ❌ 只有 `"content_change"` | 永不匹配 |
| `scope={"importance": "critical"}` | ❌ 只有 `"important"` | 永不匹配 |
| `scope={"target_key": "owner/repo"}` | ✅ 有值 | 但仅做精确匹配 |

**结论：由于 production signal vocabulary 只有一种值，InvestigationPlan 的 `scope` 机制在 production 中几乎不可用——除了 `"signal_type": "content_change"` 外，所有 scope 过滤都是无效约束。**

## 6. 诊断结论

### 6.1 四层 Vocabulary Gap

| 层 | 定义位置 | 实际状态 |
|----|----------|----------|
| **L1: GitHub API 原始指标** | `snapshots.py` | 9 个字段全部采集，8 个零消费 |
| **L2: Change Detection** | `fetch_service.py` | 仅基于 `content_hash`，丢失细粒度 |
| **L3: Event Classification** | `event_correlator.py` | 三个方法全为 stub，零映射逻辑 |
| **L4: Investigation Scoping** | `investigation_engine.py` | `scope` 机制存在但无匹配信号 |

### 6.2 修正后的完整信号链

```
[旧诊断 D4 声称]
Signal("content_change") → _derive_event_type() → "DISCARD" → Event → 零消费者

[经 D4.5 修正后]
Signal("content_change") → _derive_event_type() → "content_change" → Event → 零消费者

区别：
- _derive_event_type() 存在但不做映射（直接透传），不做 DISCARD
- "DISCARD" 属于 DecisionOutcome 语义，不属于 event classification
- 零消费者的根本原因不是 DISCARD，而是 main.py 是 stub，无运行时 pipeline
```

### 6.3 Phase 11-B / K.7 的核心发现

Phase 11-B / K.7 的核心问题**不是**"如何把 Engine 接到 pipeline"，而是：

1. **信号词汇表未定义** — production 只有一种 signal_type，InvestigationPlan 的 scope 机制没有可消费的数据。
2. **事件分类器未实现** — Event Correlator 的三个核心方法全是 stub。
3. **Policy 与 Runtime 脱钩** — Policy 定义了丰富的 EventType/ImportanceLevel 枚举，但 Runtime 层完全忽略。
4. **原始指标未利用** — GitHub API 返回的 8 个字段（stars, forks, open_issues 等）在 change detection 中零消费。

**Phase 11-B 的第一步必须是定义信号词汇表（Signal Vocabulary），而不是连接管道。**
